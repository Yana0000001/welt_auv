# welt_auv
Stingray powered AUV Welt
## 1. Анализ существующего проекта

### Отчет по структуре запуска

* **Где находится запуск:** Вся инфраструктура описывается и запускается через конфигурационный файл `docker-compose.yaml`. Запуск конкретных ROS 2 нод внутри контейнеров происходит с помощью команд `ros2 launch`.
* **Какие контейнеры участвуют:** 
  * `s_welt_auv_control` — контейнер системы управления аппаратом (команда `ros2 launch welt_launch control.launch.py`).
  * `s_welt_auv_od` — контейнер модуля обнаружения объектов / Object Detection (команда `ros2 launch welt_launch od.launch.py`).
  * `s_zed_ros2` — контейнер для работы с камерой ZED (команда `ros2 launch zed_wrapper zed_camera.launch.py`).
  * `s_rviz2` — инструмент визуализации (активируется профилями `debug` и `visualize`).
  * `s_recorder` — запись росбагов (активируется профилем `debug`).
* **Где находится compose:** Файл `docker-compose.yaml` находится в корневой директории данного проекта.
* **Где находится существующий запуск камер:** В блоке сервиса `zed_ros2`. Физические устройства пробрасываются из хост-системы внутрь контейнера через монтирование тома `- /dev:/dev`.
* **Где вы решили реализовать новый профиль:** Новый профиль зрения логичнее всего реализовать в конфигурации Docker Compose, используя встроенный механизм `profiles`. Для этого можно создать отдельный сервис для нейросетевой модели (на базе закомментированного образа `hydronautics/zed_ros2:...-neural`) и назначить ему профиль `vision` или `neural`. Это позволит запускать ресурсоемкую обработку зрения только по требованию (командой `docker-compose --profile vision up`).
## Запуск USB-камеры (Задание 2)

### 1. Пространства имен (Namespace), топики и фреймы (Требование 5)
Для однозначной идентификации данных с каждой камеры и предотвращения конфликтов в системе ROS 2, для каждого устройства настроены индивидуальные пространства имен, топики и оптические фреймы (координатные системы):

* **Фронтальная камера (Front Camera):**
  * **Namespace:** `/camera_front`
  * **Image topic:** `/stingray/topics/camera/front`
  * **CameraInfo topic:** `/stingray/topics/camera/front/camera_info`
  * **Optical frame:** `camera_front_optical_frame`

* **Нижняя камера (Bottom Camera):**
  * **Namespace:** `/camera_bottom`
  * **Image topic:** `/stingray/topics/camera/bottom`
  * **CameraInfo topic:** `/stingray/topics/camera/bottom/camera_info`
  * **Optical frame:** `camera_bottom_optical_frame`

**Соответствие условию:** Из названий топиков и фреймов прозрачно и однозначно понятно, к какому физическому направлению обзора аппарата (вперед или вниз) относятся публикуемые данные и в какой системе координат они рассчитываются.

### 2. Обеспечение устойчивого соответствия USB-камер (Требование 6)
Так как ядро Linux (V4L2 драйвер) при перезагрузке или переподключении кабелей может динамически и случайным образом менять индексы устройств (`/dev/video0`, `/dev/video1`), использовать прямые пути `/dev/video*` для постоянной конфигурации робота **категорически нельзя**.

Для решения проблемы динамических индексов физические камеры привязываются к стабильным и неизменяемым путям операционной системы:

1. **Фронтальная камера (Физическая камера А):** Привязывается через стабильный путь по физическому порту подключения на плате (хабе):
   * *Стабильный идентификатор:* `/dev/v4l/by-path/platform-3610000.usb-usb-0:2.4:1.0-video-index0` (согласно `cam.launch.py`). Этот путь жестко привязан к конкретному USB-разъему на борту робота. Даже если саму камеру заменить на аналогичную, имя устройства для системы останется прежним.
   * *Связанный топик:* `/camera_front/...`

2. **Нижняя камера (Физическая камера Б):** Привязывается по уникальному заводскому серийному номеру / ID чипа камеры:
   * *Стабильный идентификатор:* `/dev/v4l/by-id/usb-Microsoft_Microsoft®_LifeCam_HD-3000-video-index0` (согласно `cam.launch.py`). Этот путь намертво привязан к конкретному экземпляру камеры Microsoft LifeCam. В какой бы USB-порт её ни воткнули, она всегда определится системой по этому пути.
   * *Связанный топик:* `/camera_bottom/...`

**Результат:** После перезагрузки системы или скачков питания на борту АУВ, соответствие «Физический разъем/устройство ➔ Стабильный путь ➔ Пространство имен ROS 2» гарантированно сохраняется. Потоки данных никогда не перепутаются местами.

## Создать профиль запуска (Задание 8)

### 1. Реализация единого профиля запуска камер
Для объединения запуска всех настроенных USB-камер в единый сценарий был задействован механизм `profiles` в Docker Compose. В конфигурацию сервиса `usb_cameras` добавлен профиль с именем `vision`.

### 2. Логика работы профиля:
* **Команда для запуска:** `docker-compose --profile vision up -d`
* **Что происходит при запуске:**
  1. Docker Compose считывает профиль `vision` и поднимает изолированный контейнер `s_usb_cameras`.
  2. Контейнер получает привилегированный доступ к хостовому каталогу устройств `/dev`, где по стабильным путям (`by-id` и `by-path`) подтягиваются физические Фронтальная и Нижняя камеры.
  3. Внутри контейнера выполняется единый сценарий запуска `ros2 launch welt_launch cam.launch.py`, в который передаются флаги активации обеих камер (`enable_front_camera:=true` и `enable_bottom_camera:=true`).
  4. После успешного старта нод в системе ROS 2 автоматически регистрируются и начинают публиковать данные все необходимые топики:
     * `/stingray/topics/camera/front`
     * `/stingray/topics/camera/front/camera_info`
     * `/stingray/topics/camera/bottom`
     * `/stingray/topics/camera/bottom/camera_info`

## Автоматическая запись rosbag2 (Часть 2)

### 1. Реализация штатной автоматической записи данных
Для автоматического старта записи данных с камер при активации профиля зрения, конфигурация сервиса `recorder` в файле `docker-compose.yaml` была расширена. Теперь данный сервис привязан к двум профилям запуска: `debug` и `vision`.

При вызове команды запуска профиля зрения:
```bash
docker-compose --profile vision up -d
```
Docker Compose одновременно поднимает как контейнер с драйверами камер `s_usb_cameras`, так и контейнер штатного регистратора данных `s_recorder`.

### 2. Оптимизация команды записи
В отличие от отладочного режима, записывающего абсолютно все топики в системе (`-a`), для профиля `vision` команда была оптимизирована с целью экономии памяти бортового вычислителя. Запись ведется строго по целевым топикам веб-камер:
* `/stingray/topics/camera/front` (Видеопоток курсовой камеры)
* `/stingray/topics/camera/front/camera_info` (Параметры калибровки фронта)
* `/stingray/topics/camera/bottom` (Видеопоток нижней камеры)
* `/stingray/topics/camera/bottom/camera_info` (Параметры калибровки низа)

Данные сжимаются «на лету» с использованием эффективного алгоритма сжатия `zstd` пофайлово (`--compression-mode file`), файлы сохраняются в директорию `${HOME}/rosbags` на хост-машине с уникальным временным штампом в названии и автоматически завершают сессию записи через 300 секунд (5 минут) благодаря утилите `timeout`.
