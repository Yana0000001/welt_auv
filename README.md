# Отчет по сборке ROS 2 pipeline для работы с камерами и записи данных

## 1. Анализ существующего проекта и структура запуска (Часть 1)

### Отчет по структуре запуска компонентов:
* **Где находится запуск:** Вся инфраструктура описывается и координируется через конфигурационный файл **`docker/docker-compose.yml`**. Конкретные ROS 2 ноды стартуют внутри изолированных контейнеров через специализированные launch-скрипты пакета `welt_launch`.
* **Где находятся launch-файлы:** Все основные сценарии запуска исходного кода сосредоточены в пакете **`src/welt_launch/launch/`**.
* **Расположение compose-файла:** В поддиректории **`docker/`** текущего проекта, на одном уровне с контекстными папками сборки образов `control/` и `od/`.
* **Участвующие контейнеры и их назначение:** 
  * `s_welt_auv_control` — запускает главный координирующий сценарий `control.launch.py` системы управления аппаратом.
  * `s_welt_auv_od` — запускает модуль распознавания объектов Object Detection через `od.launch.py`.
  * `s_zed_ros2` — отвечает за работу со стереокамерой ZED через `zed_camera.launch.py` (существующий запуск камер, если он уже есть в проекте).
  * `s_rviz2` и `s_recorder` — инструменты визуализации и записи росбагов (активируются отладочными профилями `debug`, `visualize`).

### Разбор логики Launch-файлов:
1. **Модуль управления (`control.launch.py`):** Агрегирующий узел. Включает в себя `sauvc_launch/control.launch.py` (высокоуровневое движение) и `welt_launch/com.launch.py` (низкоуровневая связь с железом по UDP).
2. **Модуль связи (`com.launch.py`):** Поднимает `hardware_bridge_node` и UDP-драйверы для обмена пакетами с платой управления робота. Отправка идет на IP `10.42.0.111` (Порт `13053`), прием — с IP `10.42.0.186` (Порт `13050`).
3. **Симуляционный режим (`sim.launch.py`):** Имеет идентичную с управлением структуру, но в нем **закомментирован запуск пакета связи `com.launch.py`**, чтобы при работе в симуляторе виртуальный робот не пытался слать UDP-пакеты на реальные физические платы.
4. **Модуль распознавания объектов (`od.launch.py`):** Автоматически включает в себя сценарий запуска камер `cam.launch.py` и ноду детектирования объектов `sauvc_launch/od.launch.py`.

## 2. Интеграция и запуск USB-камер (Задание 2)

### Пространства имен (Namespace), топики и фреймы (Требование 5):
Для однозначной идентификации данных с каждой камеры и предотвращения конфликтов в системе ROS 2, для каждого устройства настроены индивидуальные пространства имен, топики и оптические фреймы (координатные системы):

* **Фронтальная камера (Front Camera):**
  * **Namespace:** `/camera_front`
  * **Image topic:** `/stingray/topics/camera/front`
  * **CameraInfo topic:** `/stingray/topics/camera/front/camera_info`
  * **Optical frame:** `camera_front_optical_frame`

* **Нижняя камера (Bottom Camera):**
  * **Namespace:** `/camera_bottom`
  * **Image topic:** `/stingray/topics/camera/bottom`
  * **CameraInfo topic:** `/stingray/topics/camera/bottom/camera_info`
  * **Optical frame:** `camera_bottom_optical_frame`

*Соответствие условию приемки:* Из названий топиков и фреймов прозрачно и однозначно понятно, к какому физическому направлению обзора аппарата (вперед или вниз) относятся публикуемые данные и в какой системе координат они рассчитываются.

### Обеспечение устойчивого соответствия USB-камер (Требование 6):
Использовать прямые пути `/dev/video*` для постоянной конфигурации робота категорически нельзя, так как ядро Linux (V4L2) при перезагрузке может динамически и случайно менять индексы устройств местами. 

Для решения этой проблемы физические камеры жестко привязаны к стабильным и неизменяемым путям операционной системы, описанным в `cam.launch.py`:
1. **Фронтальная камера (Физическая камера А):** Привязывается через стабильный путь по порту подключения на плате (хабе): `/dev/v4l/by-path/platform-3610000.usb-usb-0:2.4:1.0-video-index0`. Путь жестко привязан к конкретному USB-разъему на борту робота.
2. **Нижняя камера (Физическая камера Б):** Привязывается по уникальному заводскому ID чипа камеры: `/dev/v4l/by-id/usb-Microsoft_Microsoft®_LifeCam_HD-3000-video-index0`. Намертво привязана к конкретному экземпляру камеры Microsoft LifeCam.

*Результат:* После перезагрузки системы или скачков питания на борту АУВ соответствие гарантированно сохраняется, потоки данных никогда не перепутаются местами.

## 3. Профиль запуска и автоматическая запись rosbag2 (Задания 8, 9, 10, 11 и Часть 2)

### Решение по реализации нового профиля запуска (`vision`):
Новый профиль реализован в конфигурации Docker Compose (`docker/docker-compose.yml`) с использованием штатного механизма `profiles`. Он объединяет совместный старт видеосистемы и автоматического логгера.

Команда для развертывания профиля из директории `docker/`:
```bash
cd docker/
docker compose --profile vision up -d
```

### Логика параллельной работы компонентов (Требование 9):
При активации профиля зрения `vision` Docker Compose инициализирует одновременный и параллельный запуск компонентов согласно требуемой схеме:

```text
запуск vision profile
 ├──> USB camera 1 (Фронтальная / camera_front)
 ├──> USB camera 2 (Нижняя / camera_bottom)
 └──> rosbag2 recorder (s_recorder — выборочная запись логов)
```

1. **`usb_cameras`** (`s_usb_cameras`) — **Безопасное монтирование устройств:** Вместо небезопасного сквозного проброса всего хостового каталога `- /dev:/dev`, контейнер получает строго точечный доступ к конкретным файлам устройств по их устойчивым путям в Linux (`/dev/v4l/by-path/...` и `/dev/v4l/by-id/...`). Это гарантирует соблюдение принципа минимальных привилегий Docker и изолирует контейнер от остального аппаратного обеспечения хоста.
2. **`recorder`** (`s_recorder`) — параллельно стартует автоматическую штатную запись данных через `rosbag2` без необходимости ручного вызова со стороны пользователя.

### Обоснование минимального набора топиков для Computer Vision (Задание 10):
Для исключения избыточной нагрузки на дисковую подсистему бортового ПК запись ведется строго по минимально необходимому набору топиков:
1. **Топики изображений (`Image`):** Визуальные кадры фронтальной и нижней камер для работы алгоритмов Object Detection.
2. **Топики калибровки (`CameraInfo`):** Матрицы дисторсии внутренних параметров линз для исправления искажений «рыбий глаз» и метрических расчетов.
3. **Топики трансформаций (`/tf` и `/tf_static`):** Связывают оптические фреймы камер с базовой системой координат подводного аппарата (`base_link`).

**Зачем необходимы эти топики для последующей обработки видео:**
Если записать только видеопоток (`Image`), мы получим «плоскую» картинку. Без топиков `/tf` и `/tf_static` дерево пространственных связей будет уничтожено. Включение трансформаций в баг-файл критически необходимо, чтобы оффлайн-алгоритмы могли рассчитать реальные 3D-координаты обнаруженных объектов в толще воды относительно робота.

## 4. Системные требования к надежности хранения данных (Задания 11, 13, 14, 15)

### Изоляция сессий записи логов (Задание 11):
Имя выходной папки rosbag2 генерируется динамически с использованием системных переменных времени Linux:
* **Шаблон именования:** `$(date +%Y-%m-%d_%H-%M-%S)` (Формат: `ГГГГ-ММ-ДД_ЧЧ-ММ-СС`).
Каждый запуск создает изолированную поддиректорию внутри папки логов, что полностью исключает случайную перезапись старых логов новыми данными при повторных тестах.

### Хранение на накопителе, разбиение и контроль места:
* **Хранение (Пункт 12):** Каталог с логами вынесен на физический хост-накопитель через volume `${HOME}/rosbags:/rosbags`, что сохраняет данные после удаления контейнера.
* **Разбиение записи (Пункт 13):** Настроен параметр `--max-bag-size 524288000` (500 МБ). Запись автоматически разбивается по размеру, защищая файлы от повреждения при сбоях.
* **Контроль места (Пункт 14):** При переполнении SSD утилита `rosbag2` выбрасывает ошибку `IOError: No space left on device` в консоль контейнера, останавливая процесс, что сразу становится явно видно оператору.

### Корректное завершение (Пункт 15):
В конфигурацию Docker Compose добавлен флаг `init: true`. При плановой или экстренной остановке проекта (`docker compose stop` / `Ctrl+C`) контейнер корректно транслирует сигнал `SIGINT` в процесс `ros2 bag record`. Регистратор успевает закрыть индексы сессии, исключая ситуацию повреждения bag-файла.

## 5. Настройка QoS и воспроизведение (Задания 16, 17)

### Параметры QoS (Пункт 16):
Топики камер используют профиль `SensorData` (Best Effort доставка, глубина очереди 5), снижающий сетевые задержки. Регистратор `rosbag2` автоматически подстраивается под него при записи. При оффлайн-воспроизведении багов применяется файл переопределения профилей качества (Reliable) для совместимости со стандартными подписчиками:
```bash
ros2 bag play /rosbags/<название_сессии> --qos-profile-overrides-path qos_override.yaml
```

### Проверка воспроизведения (Пункт 17):
Проверка осуществляется последовательным запуском утилит инспекции и проигрывания:
```bash
ros2 bag info /rosbags/<название_сессии>
ros2 bag play /rosbags/<название_сессии>
```
Данные успешно считываются, восстанавливая исходный видеопоток и дерево пространственных трансформаций.
